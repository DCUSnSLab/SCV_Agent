# FTA (Fleet Telemetry Agent) — 아키텍처 설계서 (v0.1 Draft)

- 작성일: 2026-07-19
- 관련 문서: 01_요구사항명세서.md

---

## 1. 설계 원칙

1. **선언적 구성**: 파이프라인은 코드가 아니라 YAML 설정으로 정의한다. 로봇 50대 각각의 데이터 선정·전략 차이는 설정 차이로만 표현된다.
2. **전략의 플러그인화**: 샘플러, 코덱, 전송 계층은 모두 공통 인터페이스 + 레지스트리 구조로, 신규 알고리즘은 클래스 하나 추가로 확장한다.
3. **로봇 무영향 격리**: 별도 프로세스, best-effort 구독, 리소스 상한. 에이전트는 로봇에게 "존재하지 않는 것처럼" 동작해야 한다.
4. **불안정 네트워크 전제**: LTE/5G의 CGNAT, IP 변경, 음영지역 단절을 정상 상황으로 취급하고 설계한다. 연결이 끊기는 것은 예외가 아니라 일상이다.
5. **전송 계층 중립**: v1은 MQTT지만, 아키텍처는 특정 프로토콜에 결합되지 않는다. 이 추상화는 향후 자체 프로토콜 연구의 실험 플랫폼 역할을 겸한다.

## 2. 전체 구조

```

│                                                                             │

│        │  ROS2 topics (DDS)                                                 │
│        ▼                                                                    │
│  ┌──────────────────── FTA 에이전트 (별도 프로세스) ────────────────────┐        │
│  │                                                                    │        │

│  │        ▲                 (Sampler→Codec)        │            Manager│        │
│  │        │                                        ▼               │  │        │
│  │   ConfigLoader                            DiskBuffer            │  │        │
│  │   (YAML 검증/로드)                       (store&forward)        │  │        │

                                                              │
                                                    테스트 리시버 / (향후) 수집 서버
```

## 3. 컴포넌트 상세

### 3.1 ConfigLoader
- YAML 설정을 로드·스키마 검증하고 파이프라인 명세 객체로 변환.
- 검증 실패 시 즉시 종료 + 원인 명시 (조용한 오동작 금지).

**설정 스키마 예시:**
```yaml
agent:
  robot_id: ${ROBOT_ID}            # 환경변수 주입
  ros_domain_id: 42
  resource:
    cpu_limit_pct: 20
    mem_limit_mb: 512
    bandwidth_limit_kbps: 1000
  buffer:
    dir: /var/lib/fta/buffer
    max_disk_mb: 2048
    retention: { critical: keep_all, state: keep_latest }

transport:
  type: mqtt                        # mqtt | zenoh | custom (레지스트리 키)
  mqtt:
    host: telemetry.example.ac.kr
    port: 8883
    tls: true
    client_id: fta-${ROBOT_ID}
    keepalive_sec: 30

pipelines:
  - name: odom
    topic: /odom
    msg_type: nav_msgs/msg/Odometry
    sampler: { type: rate, hz: 2 }
    codec:   { type: cdr_zstd }
    priority: high

  - name: gps
    topic: /gps/fix
    msg_type: sensor_msgs/msg/NavSatFix
    sampler: { type: rate, hz: 2 }
    codec:   { type: cdr_zstd }
    priority: high

  - name: planned_path
    topic: /plan
    msg_type: nav_msgs/msg/Path
    sampler: { type: passthrough }        # 비주기 1회 발행 → 수신 즉시 전송
    codec:   { type: cdr_zstd }           # 포즈 배열이라 압축 효율 높음
    priority: high
    qos: { reliability: reliable, durability: transient_local, depth: 1 }

  - name: vehicle_estop
    topic: /vehicle/status
    sampler: { type: event, field: estop, condition: changed }
    codec:   { type: cbor }
    priority: critical

  - name: front_cam_snapshot
    topic: /camera/front/image_raw/compressed
    sampler: { type: on_demand }
    codec:   { type: jpeg, quality: 60, max_width: 640 }
    priority: low

  - name: lidar_preview
    topic: /lidar/points
    sampler: { type: rate, hz: 0.2 }
    codec:   { type: voxel_zstd, voxel_size: 0.2 }
    priority: low
    enabled: false                  # 기본 비활성, 필요 시 켬
```

### 3.2 SubscriptionManager
- 파이프라인 명세에 따라 generic subscription 생성 (타입 introspection 활용).
- 기본 QoS: `best_effort, depth=1~5` (파이프라인별 override 가능).
- 콜백에서는 최소 작업만 수행하고 즉시 파이프라인 입력 큐로 넘긴다 (executor 블로킹 금지).

### 3.3 Pipeline (토픽당 1개)
```
[ROS msg] → Sampler.decide(msg) → (통과 시) Codec.encode(msg) → Envelope 부착 → PriorityQueue.push
```
- Sampler와 Codec은 각각 인터페이스를 구현한 플러그인:

```cpp
// 개념 인터페이스 (C++ 기준)
struct ISampler {
  virtual Decision decide(const RosMessageView& msg, const Clock& now) = 0;
  // Decision: PASS | DROP | PASS_AND_FLUSH(이벤트: 즉시 전송 요구)
};

struct ICodec {
  virtual EncodedPayload encode(const RosMessageView& msg) = 0;
  // EncodedPayload: bytes + encoding_id (예: "cdr+zstd", "jpeg", "voxel0.2+zstd")
};

struct ITransport {
  virtual void connect(const TransportConfig&) = 0;
  virtual PublishResult publish(const Envelope&, ReliabilityClass) = 0;
  virtual ConnState state() const = 0;
  // 연결 상태 변화 콜백, 통계 조회 등
};
```
- 각 구현체는 문자열 키로 **레지스트리에 등록** → 설정의 `type:` 값과 매칭. 새 알고리즘 추가 = 클래스 작성 + 등록 한 줄.

### 3.4 Envelope (공통 메시지 봉투)
```
Envelope {
  robot_id: string
  seq: uint64            # 파이프라인별 단조 증가 (손실 감지용)
  pipeline: string       # 설정상의 name
  src_topic: string
  msg_type: string
  stamp_ros: time        # 메시지 헤더 타임스탬프
  stamp_agent: time      # 에이전트 처리 시각 (지연 측정용)
  encoding: string
  payload: bytes
}
```
- envelope 직렬화: CBOR (자기서술적, 바이너리 효율, 언어 중립).
- payload 기본: ROS 원본 CDR + zstd. 수신측(향후 서버)이 CDR을 그대로 rosbag 기록에 재사용할 수 있어 유리하다.

### 3.5 PriorityQueue + UplinkManager
- 우선순위 4단계: `critical > high > normal > low`.
- UplinkManager는 토큰 버킷으로 대역폭 상한을 강제하고, 여유 대역폭을 우선순위 순으로 배분.
- 큐 포화 시 정책: low/normal은 오래된 것부터 드롭, high는 최신값 유지(conflation), critical은 드롭 금지 → DiskBuffer로 이관.
- 드롭·처리량 통계는 SelfTelemetry로 집계.

### 3.6 DiskBuffer (Store & Forward)
- 단절 감지 시: critical/이벤트 → 전량 디스크 기록, 상태 데이터 → 파이프라인별 최신 N개만 유지.
- 재연결 시 재전송 순서: critical(오래된 것부터) → 단절 중 최신 상태 스냅샷 → 평시 흐름 복귀.
- append-only 세그먼트 파일 + 인덱스, 디스크 상한 도달 시 오래된 low부터 삭제. 에이전트 재시작 후에도 복구 가능해야 한다.

### 3.7 Transport — MqttTransport (v1)
- MQTT v5, TLS, outbound 연결 상시 유지 (CGNAT 대응).
- **토픽 네임스페이스:**
```
fleet/{robot_id}/state/{pipeline}     QoS 0   상태 데이터
fleet/{robot_id}/event/{pipeline}     QoS 1   이벤트 (손실 불가)
fleet/{robot_id}/bulk/{pipeline}      QoS 0   대용량 (스냅샷 등)
fleet/{robot_id}/agent/health         QoS 0   에이전트 자체 상태 (heartbeat 겸용)
fleet/{robot_id}/agent/registry_status QoS 1  레지스트리 동기화 결과 (지원/미지원 인터페이스 보고)
fleet/{robot_id}/sys/lwt              QoS 1   Last Will (비정상 오프라인 감지)
fleet/{robot_id}/cmd/{interface}      QoS 1   다운링크 명령 (v1: topic/service)
fleet/{robot_id}/cmd_result/{interface} QoS 1 명령 실행 결과 응답
fleet/registry                        retained  인터페이스 레지스트리 배포 (fleet 공통)
fleet/{robot_id}/registry             retained  로봇별 레지스트리 override (선택)
```
- 재연결: 지수 백오프 (1s → 2s → ... → max 30s) + jitter. LTE↔WiFi 전환에 의한 IP 변경 시에도 동일 로직으로 복구.
- 브로커 후보: EMQX 또는 Mosquitto (테스트 단계는 Mosquitto로 충분, 50대 규모도 문제 없음 — 정식 선정은 서버 프로젝트에서).

### 3.8 ResourceGovernor
- 주기적으로 자체 CPU/메모리/송신 대역폭을 측정.
- 임계 초과 시 절제 순서: bulk 파이프라인 일시 정지 → low 드롭율 증가 → 샘플링 주기 하향 (adaptive 훅).
- systemd 서비스 + `CPUQuota`, `MemoryMax` 로 OS 레벨 방어선 병행 (에이전트 자체 제어의 백스톱).

### 3.9 SelfTelemetry
- 파이프라인별 in/out/drop 카운트, 큐 길이, 버퍼 사용량, RTT, 연결 상태를 `agent/health`로 주기 보고 + 로컬 ROS2 토픽 발행.
- 이 데이터 자체가 이후 "적응형 샘플링" 연구의 입력이 된다.

### 3.10 온디맨드 메커니즘
- 온디맨드 트리거는 두 가지로 제공:
  1. **로컬 ROS2 서비스** (`/fta/request_snapshot`) — 로봇 내부/현장 디버깅용
  2. **다운링크 인터페이스** — 스냅샷 요청을 service kind 인터페이스로 레지스트리에 등록하면 서버발 온디맨드가 자연스럽게 지원됨 (§3.11의 일반 메커니즘으로 흡수)

### 3.11 다운링크 서브시스템 — 동적 인터페이스 프로비저닝

> 관련 요구사항: 01 문서 FR-9, NFR-7(협상 불가 안전 조항). 핵심 아이디어: 다운링크 가능 대상을 하드코딩하지 않고, 레지스트리에 등록된 인터페이스 정의를 에이전트가 동기화하여 런타임에 통신 창구를 구성한다.

**구성 요소:**

```
              fleet/registry (retained) ──▶ RegistrySyncManager
                                             │ 버전 해시 비교 → 변경분 적용
                                             │ 로컬 typesupport 존재 검증
                                             │ → registry_status 보고
                                             ▼
  fleet/{id}/cmd/{interface} ──▶ CommandExecutor
                                   │ 검증 체인 (NFR-7.5 순서 고정):
                                   │  ① 레지스트리 등록 여부
                                   │  ② payload JSON Schema 검증
                                   │  ③ TTL (issued_at + ttl 미경과)
                                   │  ④ 멱등성 (cmd_id LRU 캐시)
                                   ▼
                            JsonMessageConverter
                                   │ rosidl introspection 기반 JSON → ROS msg
                                   ▼
                       kind=topic → GenericPublisher.publish → "accepted"
                       kind=service → ServiceClient.call(timeout) → 결과 JSON화
                                   │
                                   ▼
                    fleet/{id}/cmd_result/{interface}  +  감사 로그(AuditLog)
```

- **RegistrySyncManager**: 레지스트리는 MQTT retained 메시지로 배포한다. retained 특성상 에이전트는 구독 즉시 최신본을 받고, 갱신 시 자동 재수신되므로 별도 폴링·알림 채널이 불필요하다. 각 인터페이스의 `ros_type`이 로컬 typesupport 라이브러리에 존재하는지 기동 시 검증하고, 지원/미지원 목록을 `registry_status`로 보고한다 — 서버/웹은 이 보고를 근거로 "이 로봇에 이 명령을 보낼 수 있는지"를 UI에 반영할 수 있다.
- **CommandExecutor**: 검증 체인의 각 단계는 실패 시 즉시 `rejected`/`expired` 응답 + 감사 로그를 남기고 종료한다. 검증을 우회하는 실행 경로는 존재하지 않는다 (NFR-7.5).
- **JsonMessageConverter**: 에이전트측 변환(D7 확정)의 구현체. introspection typesupport로 타입 구조를 런타임 순회하며 JSON 필드를 매핑한다. 커스텀 타입도 차량에 typesupport가 설치되어 있는 한 동일하게 동작하므로 타입별 코드가 필요 없다.
- **테스트 레지스트리 도구**: 파일(YAML/JSON) 또는 SQLite에 정의된 인터페이스 목록을 retained 메시지로 발행하는 소형 CLI. 정식 레지스트리 DB·웹 UI(서버 프로젝트)가 나오기 전까지의 개발·검증 수단이며, 발행 포맷이 곧 두 프로젝트 간 계약이 된다.

**레지스트리 항목 스키마 (계약):**
```yaml
interfaces:
  - interface_id: set_goal
    name: "목적지 설정"
    kind: topic                      # topic | service (action은 v2)
    ros_type: geometry_msgs/msg/PoseStamped
    target: /goal_pose
    qos: { reliability: reliable, depth: 1 }
    schema: { ... JSON Schema ... }  # payload 검증용
    permission_level: L2             # L0 조회 / L1 설정 / L2 작동·주행
    default_ttl_sec: 30
    version: 3
```

## 4. 주요 시나리오별 동작 메커니즘

### 4.1 평시 상태 데이터 흐름
1. `/odom` 50Hz 수신 → `rate(2Hz)` 샘플러가 48/50 드롭
2. 통과분 CDR+zstd 인코딩 → envelope 부착 → high 큐
3. UplinkManager가 토큰 버킷 내에서 `fleet/r01/state/odom` QoS 0 발행
4. 종단 지연 목표 ≤ 1s

### 4.2 이벤트 발생 (E-Stop)
1. `/vehicle/status`에서 estop 필드 변화 → `event` 샘플러 PASS_AND_FLUSH
2. critical 큐 → 대역폭 상한과 무관하게 최우선 즉시 발행 (QoS 1, 브로커 ACK 확인)
3. 미ACK 상태에서 단절 시 DiskBuffer 보존 → 재연결 시 최우선 재전송

### 4.3 네트워크 단절 → 복구 (음영지역 통과)
1. keepalive 실패로 단절 감지 → UplinkManager가 버퍼 모드 전환
2. critical/이벤트: 디스크 기록 / 상태: 최신값만 유지 / bulk: 폐기
3. 백오프 재접속 → 성공 시 critical 백로그부터 순차 재전송 → 평시 복귀
4. 서버는 LWT로 단절을, health 재개로 복귀를 감지

### 4.4 스냅샷 온디맨드
1. `/fta/request_snapshot front_cam` 호출
2. `on_demand` 샘플러가 다음 프레임 1장 통과 → JPEG(q60, 640px) 인코딩
3. `bulk/front_cam_snapshot` 발행 (low 우선순위 — 상태 데이터를 밀어내지 않음)

### 4.5 다운링크 — 목적지 지정 (동적 인터페이스 경유)
1. 웹 클라이언트에서 지도의 한 점 클릭 → 서버가 `fleet/r01/cmd/set_goal` 발행: `{cmd_id, issued_at, ttl: 30, issuer, payload: {pose: {...}}}`
2. 에이전트 검증 체인 통과 (등록 여부 → 스키마 → TTL → 멱등성)
3. JSON → `PoseStamped` 변환 → `/goal_pose` 발행 → `accepted` 응답 + 감사 로그
4. 차량 Nav 스택이 목적지 수신·주행 시작 — 이후 주행 상태는 업링크 상태 데이터(odom, GPS, 차량 상태)로 모니터링
5. 만약 로봇이 음영지역에 있어 명령이 35초 뒤 도착했다면: TTL 초과 → 실행하지 않고 `expired` 응답 (NFR-7.1)

### 4.6 다운링크 — 신규 인터페이스 추가 (코드 수정 없음)
1. 차량 개발자가 커스텀 타입 인터페이스를 레지스트리에 등록 (v1: 테스트 레지스트리 도구, 향후: 웹 UI)
2. retained 메시지 갱신 → 전 차량 에이전트가 자동 재수신
3. 각 에이전트가 로컬 typesupport 검증 → 지원 여부를 `registry_status`로 보고
4. 해당 타입이 설치된 차량에서만 인터페이스 활성화 — 서버/웹은 보고를 근거로 명령 가능 차량을 구분

## 5. 기술 스택 (제안)

| 항목 | 제안 | 근거 |
|---|---|---|
| 언어 | **C++20 / rclcpp** | 리소스 상한 통제, generic subscription + CDR raw 접근 용이, 장기 상주 프로세스 안정성 |
| (대안) | Python/rclpy 프로토타입 | 개발 속도 우선 시. 단, 이미지/PCL 처리·GIL 고려 필요 |
| MQTT | Eclipse Paho C++ (또는 mosquitto lib) | 성숙도 |
| 압축 | zstd (레벨 설정 가능), OpenCV(JPEG), PCL(voxel) | 표준적 |
| JSON↔msg 변환 | rosidl introspection typesupport (+ JSON Schema 검증 라이브러리) | 다운링크 D7 — 타입별 코드 없이 커스텀 타입 대응 |
| 빌드/배포 | colcon 패키지 + systemd 서비스 (+ 선택: 컨테이너) | 50대 프로비저닝 고려 |
| 테스트 | gtest + rosbag 재생 통합 테스트 + 테스트 리시버 + 테스트 레지스트리 도구 | NFR-6, FR-9.9 |

> D1(언어)은 최종 확정 전. 랩 인력의 숙련도가 Python 쪽이면 "Python으로 M1~M2 프로토타입 → 병목 확인 후 C++ 전환" 경로도 유효하다.

## 6. 확장 로드맵과 연구 연계

| 단계 | 내용 |
|---|---|
| v1 | 업링크 텔레메트리 + **다운링크(topic/service, 동적 인터페이스)** (본 문서 범위) |
| v1.x | adaptive 샘플러(네트워크 인지형), Draco, 카메라 저빈도 프리뷰, 타입 스키마 자동 추출·업로드(D10) |
| v2 | 다운링크 action 지원(goal/feedback/cancel), 발신자 인증·권한 검증 완성(서버 연계), 영상 실시간 스트리밍(WebRTC 별도 채널) |
| 연구 A | **네트워크 적응형·중요도 기반 fleet 텔레메트리 스케줄링** — 제한 대역폭 하 다수 로봇의 데이터 가치 기반 대역 배분. SelfTelemetry 데이터가 실험 근거 |
| 연구 B | **전송 프로토콜 벤치마크 플랫폼** — Transport 추상화 위에서 MQTT vs Zenoh vs 자체 프로토콜(DDS 대체 연구)을 동일 워크로드로 정량 비교 (지연·손실·재연결·대역 효율). rosbag 재생 기반 재현 가능 실험 |
| 연구 C | DDS QoS ↔ WAN 전송 신뢰수준 매핑 체계화 |
| 연구 D | **레지스트리 기반 동적 인터페이스 프로비저닝** — DDS 도메인 경계를 넘는 fleet 규모 ROS2 인터페이스 관리. REP-2011(type description distribution)과의 접점, rosbridge/Foxglove 대비 차별점(커스텀 타입 무코드 대응, 안전 검증 체인 내장)을 시스템 논문으로 정리 가능 |
