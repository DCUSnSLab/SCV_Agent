# ROS2 Fleet Telemetry Agent — 요구사항 명세서 (v0.1 Draft)

- 프로젝트명(가칭): **FTA (Fleet Telemetry Agent)**
- 작성일: 2026-07-19
- 상태: 초안 — 논의용

---

## 1. 개요

### 1.1 배경
캠퍼스 내 순찰 및 물류 이동을 목표로 하는 ROS2 기반 실외 자율주행 이동체(로봇)를 다수 운영할 예정이며, 이를 위한 웹 기반 모니터링·컨트롤 시스템이 별도로 개발 중이다. 그러나 현재 로봇(ROS2/DDS 도메인)과 중앙 서버 사이의 데이터 전달 수단이 부재하여 모니터링 시스템이 동작하지 못하는 상태이다.

### 1.2 목표
로봇 내부에서 동작하는 **텔레메트리 에이전트(ROS2 노드)** 를 개발한다. 에이전트는 ROS2 토픽 데이터를 갈무리하여, 데이터 특성에 맞는 샘플링·압축을 적용한 후 중앙 서버로 전송한다.

### 1.3 v1 범위
| 구분 | 포함 여부 |
|---|---|
| 업링크 (로봇 → 서버) | **포함** |
| 다운링크 (서버 → 로봇) | **포함** — 동적 인터페이스 방식, v1은 topic 발행 + service 호출. action은 확장 예약 |
| 차량측 에이전트 | **포함 (본 프로젝트의 핵심)** |
| 서버측 시스템 | 제외 — 검증용 임시 테스트 리시버만 포함 |
| 웹 모니터링 UI | 제외 (별도 프로젝트) |

### 1.4 운영 환경
- 네트워크: **LTE/5G 라우터(주)** + 캠퍼스 Wi-Fi(보조)
  - 이동통신망 특성상 로봇은 CGNAT 뒤에 위치 → 모든 연결은 로봇에서 outbound로 개시
  - LTE↔WiFi 전환 시 IP 변경 및 순단 발생 가능
  - 커버리지 음영지역에서 수 초~수 분 단절 가능
- 로봇 대수: 초기 2~3대 → 최종 **50대**
- 로봇 플랫폼: ROS2 기반 (배포판 확정 필요 — Humble/Jazzy 등)

## 2. 용어
| 용어 | 정의 |
|---|---|
| 에이전트 (Agent) | 로봇 내에서 동작하며 데이터를 수집·가공·전송하는 본 프로젝트 산출물 |
| 파이프라인 (Pipeline) | 하나의 ROS2 토픽에 대한 [구독 → 샘플링 → 직렬화 → 압축 → 큐잉] 처리 단위 |
| 샘플러 (Sampler) | 데이터 전송 빈도/조건을 결정하는 플러그인 컴포넌트 |
| 코덱 (Codec) | 직렬화 + 압축을 담당하는 플러그인 컴포넌트 |
| 전송 계층 (Transport) | 서버와의 실제 통신을 담당하는 교체 가능 컴포넌트 (MQTT, Zenoh, 자체 프로토콜 등) |
| 상태 데이터 | 소용량·주기성 데이터 (odom, IMU 요약, 배터리, 차량 상태 등) |
| 대용량 데이터 (Bulk) | 카메라 영상, LiDAR 포인트클라우드 등 |
| 이벤트 데이터 | 진단 경고, 상태 변화, E-Stop 등 손실 불가 데이터 |

## 3. 데이터 인벤토리 및 전송 정책 (초안)

> ⚠️ 실측 주기/크기는 실제 로봇에서 `ros2 topic hz/bw`로 확인 후 확정 필요

| 데이터 | 예상 메시지 타입 | 원 주기(예상) | 전송 정책(제안) | 분류 |
|---|---|---|---|---|
| 휠 오도메트리 | `nav_msgs/Odometry` | 50 Hz | 주기 다운샘플 2~5 Hz | 상태 |
| IMU | `sensor_msgs/Imu` | 100~200 Hz | 다운샘플 5~10 Hz 또는 윈도우 통계(평균/최대) | 상태 |
| 차량 데이터 (속도·조향·주행모드·E-Stop 등) | 커스텀 msg | 10~50 Hz | deadband(변화 감지) + 상태변화 시 즉시 | 상태/이벤트 |
| 배터리 | `sensor_msgs/BatteryState` | 1~10 Hz | deadband (예: SoC 0.5%p 변화 시) | 상태 |
| 디바이스 진단 (CPU·온도·디스크·노드 생존) | `diagnostic_msgs/DiagnosticArray` | 1 Hz | 저주기(0.2 Hz) + WARN/ERROR 발생 시 즉시 | 상태/이벤트 |
| 위치 추정 결과 (localization pose) | `geometry_msgs/PoseWithCovarianceStamped` 등 | 10~50 Hz | 주기 다운샘플 1~2 Hz | 상태 |
| GPS | `sensor_msgs/NavSatFix` | 10 Hz | 주기 다운샘플 1~2 Hz (옵션: 이동량 deadband 병용) | 상태 |
| 전역 계획 경로 | `nav_msgs/Path` | 비주기 — 경로 생성 시 1회 발행 | passthrough — 수신 즉시 전송. **transient_local(latched) 구독 필요** (에이전트가 발행 이후에 기동해도 마지막 경로 수신 보장) | 상태/이벤트 |
| 카메라 | `sensor_msgs/CompressedImage` | 15~30 Hz | **온디맨드 스냅샷(JPEG)** + 옵션: 저빈도 프리뷰(0.5~1 fps) | Bulk |
| LiDAR | `sensor_msgs/PointCloud2` | 10~20 Hz | **온디맨드** + 복셀 다운샘플 후 압축, 또는 저빈도(0.2~0.5 Hz) | Bulk |

**핵심 정책:** 상태·이벤트 데이터는 상시 전송, Bulk 데이터는 기본 차단·온디맨드(또는 저빈도 프리뷰)로 이원화한다. 50대 × LTE 환경에서 통신 비용과 서버 수신 부하를 통제하기 위함이다.

## 4. 기능 요구사항 (Functional Requirements)

### FR-1. 데이터 수집
- **FR-1.1** 에이전트는 설정 파일에 명시된 ROS2 토픽을 동적으로 구독할 수 있어야 한다 (코드 수정 없이 토픽 추가/제거).
- **FR-1.2** 구독 시 메시지 타입을 설정 또는 런타임 introspection으로 결정할 수 있어야 한다 (generic subscription).
- **FR-1.3** 모든 구독은 로봇 시스템에 영향을 주지 않도록 QoS를 best-effort, 얕은 depth로 기본 설정한다 (토픽별 override 허용).
- **FR-1.4** 설정에 없는 토픽은 구독하지 않는다 (opt-in 방식).
- **FR-1.5** 1회성/latched 발행 토픽(예: 전역 계획 경로) 대응을 위해 파이프라인별 QoS durability(`transient_local`) 및 reliability 설정을 지원해야 한다.

### FR-2. 샘플링 (Sampler 플러그인)
- **FR-2.1** 샘플러는 공통 인터페이스를 갖는 클래스로 구현되며, 토픽별로 설정에서 선택·조합 가능해야 한다.
- **FR-2.2** v1에서 다음 샘플러를 제공한다:
  - `rate`: 목표 주기(Hz)로 다운샘플
  - `deadband`: 지정 필드 값의 변화량이 임계값을 넘을 때만 통과
  - `event`: 조건(예: diagnostics level ≥ WARN) 충족 시 즉시 통과
  - `on_demand`: 서버(또는 로컬 서비스) 요청 시 1회 통과
  - `passthrough`: 무가공 통과
- **FR-2.3** 샘플러 파라미터(Hz, 임계값, 대상 필드 등)는 설정 파일로 지정한다.
- **FR-2.4** (확장 예약) 네트워크 상태에 따라 파라미터를 동적 조절하는 `adaptive` 샘플러를 추가할 수 있는 구조여야 한다.

### FR-3. 직렬화 및 압축 (Codec 플러그인)
- **FR-3.1** 코덱은 공통 인터페이스를 갖는 클래스로 구현되며, 토픽별로 선택 가능해야 한다.
- **FR-3.2** v1에서 다음을 제공한다:
  - 범용: CDR 원본 passthrough / CBOR(또는 JSON) 변환 + zstd 압축
  - 이미지: JPEG 재인코딩(품질 설정 가능)
  - 포인트클라우드: 복셀 다운샘플 + zstd (Draco는 v1.x 옵션)
- **FR-3.3** 페이로드에는 인코딩 방식 식별자가 포함되어 수신측에서 디코딩 방법을 알 수 있어야 한다.

### FR-4. 전송
- **FR-4.1** 전송 계층은 추상 인터페이스(`Transport`)로 분리하며, v1 기본 구현은 **MQTT v5 (TLS)** 로 한다.
- **FR-4.2** 로봇은 서버로 outbound 연결을 개시·유지한다 (CGNAT 대응).
- **FR-4.3** 데이터 분류별 전송 신뢰수준을 지원한다: 상태=at-most-once(QoS 0), 이벤트=at-least-once(QoS 1).
- **FR-4.4** 로봇 생존 여부를 서버가 감지할 수 있어야 한다 (MQTT LWT + 주기적 heartbeat).
- **FR-4.5** 페이로드는 공통 envelope(robot_id, seq, 원 토픽명, 타입, ROS 타임스탬프, 에이전트 타임스탬프, 인코딩)을 포함한다.
- **FR-4.6** 토픽 네임스페이스는 `fleet/{robot_id}/...` 체계를 따라 50대 규모에서 서버측 라우팅이 가능해야 한다.
- **FR-4.7** (확장 예약) 학생 연구 중인 자체 프로토콜, Zenoh 등을 `Transport` 구현체 추가만으로 교체할 수 있어야 한다.

### FR-5. 버퍼링 및 신뢰성
- **FR-5.1** 전송 전 데이터는 우선순위 큐(critical > high > normal > low)에 적재되며, 대역폭 부족 시 낮은 우선순위부터 드롭한다.
- **FR-5.2** 네트워크 단절 시 이벤트/critical 데이터는 로컬 디스크에 보존(store & forward)하고, 재연결 후 재전송한다.
- **FR-5.3** 단절 버퍼는 최소 30분 분량의 이벤트·저주기 상태 데이터를 보존할 수 있어야 하며, 디스크 사용 상한을 설정할 수 있다.
- **FR-5.4** 상태 데이터는 단절 중 최신값 위주로 보존한다 (오래된 고주기 데이터 재전송으로 대역폭 낭비 금지 — 정책 설정 가능).
- **FR-5.5** 재연결은 지수 백오프로 자동 수행하며, LTE↔WiFi 전환에 따른 IP 변경에도 세션을 재수립한다.

### FR-6. 설정 및 관리
- **FR-6.1** 모든 파이프라인 구성(토픽, 샘플러, 코덱, 우선순위, QoS)은 단일 YAML 설정 파일로 선언한다.
- **FR-6.2** robot_id, 서버 주소, 인증 정보는 설정/환경변수로 주입한다 (로봇 50대 프로비저닝 고려).
- **FR-6.3** 설정 오류(존재하지 않는 샘플러, 잘못된 파라미터)는 기동 시 검증되어 명확한 오류 메시지를 출력한다.
- **FR-6.4** (v1.x) 런타임 설정 리로드 및 서버발 파이프라인 on/off 제어를 위한 확장 포인트를 마련한다.

### FR-7. 에이전트 자체 관측성
- **FR-7.1** 에이전트는 자신의 상태(파이프라인별 처리량, 드롭 수, 큐 길이, 전송 대역폭, 버퍼 사용량, 연결 상태)를 텔레메트리로 서버에 보고한다.
- **FR-7.2** 위 상태를 로컬 ROS2 토픽으로도 발행하여 로봇 내에서 진단 가능해야 한다.
- **FR-7.3** 구조화된 로그를 남기며 로그 레벨을 설정할 수 있다.

### FR-8. 테스트 리시버 (검증용, 최소 구현)
- **FR-8.1** MQTT 브로커 + 구독 클라이언트로 구성된 임시 수신기를 제공한다.
- **FR-8.2** 수신 데이터를 디코딩하여 콘솔 출력 및 파일(jsonl 등)로 기록할 수 있다.
- **FR-8.3** 수신 통계(로봇별 메시지 수, 대역폭, 지연)를 출력하여 에이전트 검증에 사용한다.
- **FR-8.4** 본 리시버는 검증 목적이며, 정식 서버는 별도 프로젝트로 진행한다 (→ 03 문서 참조).

### FR-9. 다운링크 — 동적 인터페이스 (Dynamic Interface Provisioning)

> 설계 원칙: 다운링크로 전송 가능한 대상은 코드에 하드코딩하지 않는다. 개발자가 레지스트리에 인터페이스 정의를 등록하면, 에이전트가 이를 동기화하여 런타임에 해당 통신 창구를 스스로 구성한다.

- **FR-9.1** 다운링크 인터페이스는 레지스트리에 등록된 정의에 의해서만 활성화된다 (opt-in). 등록되지 않은 대상으로의 발행·호출은 불가능해야 한다.
- **FR-9.2** 레지스트리 항목은 최소 다음 필드를 포함한다: `interface_id`, `name`, `kind`(topic | service), `ros_type`, `target`(토픽/서비스명), `qos`, `schema`(payload 검증용 JSON Schema), `permission_level`, `default_ttl`, `version`.
- **FR-9.3** 에이전트는 서버 접속 시 및 변경 통지 수신 시 레지스트리를 동기화하고, 각 인터페이스의 `ros_type`이 로컬 typesupport에 존재하는지 검증하여 지원/미지원 목록을 서버에 보고한다.
- **FR-9.4** 명령은 공통 명령 envelope으로 수신한다: `{ cmd_id, interface_id, issued_at, ttl, issuer, payload(JSON) }`.
- **FR-9.5** 페이로드 변환은 에이전트측에서 수행한다: 서버/웹은 JSON만 전송하고, 에이전트가 로컬 introspection typesupport로 JSON → ROS 메시지 변환 후 실행한다. 서버는 ROS 타입 구조를 알 필요가 없어야 한다.
- **FR-9.6** kind별 실행 방식:
  - `topic`: 대상 토픽으로 1회 발행 후 `accepted` 응답
  - `service`: 대상 서비스 호출(타임아웃 설정 가능, 기본 10초) 후 응답 값을 JSON으로 변환하여 결과 반환
- **FR-9.7** 모든 명령은 결과 응답을 갖는다: `{ cmd_id, status: accepted | done | failed | rejected | expired, detail }`. 무응답으로 끝나는 명령이 있어서는 안 된다.
- **FR-9.8** action 지원은 v1에서 제외하며, kind 확장이 가능한 구조로만 설계한다 (goal/feedback/result 대응은 v2).
- **FR-9.9** 정식 레지스트리 저장소(DB)와 웹 등록 UI는 서버 프로젝트 범위이다. 본 프로젝트는 (a) 레지스트리 스키마 및 동기화 프로토콜 **정의**, (b) 에이전트측 동기화·검증·실행 **구현**, (c) 테스트용 최소 레지스트리 도구(파일/SQLite 기반) 제공을 담당한다.
- **FR-9.10** 타입 스키마 등록은 v1에서는 개발자 수동 등록으로 하며, 에이전트는 로컬 typesupport와의 정합성 검증만 수행한다. 차량에서의 스키마 자동 추출·업로드는 v1.x 확장으로 한다.
- **FR-9.11** 수신·실행·거부된 모든 다운링크 명령은 감사 로그(audit log)로 기록한다 (cmd_id, issuer, 시각, 검증 결과, 실행 결과).

### NFR-1. 로봇 시스템 무영향 (최우선)
- **NFR-1.1** 에이전트는 자율주행 스택과 분리된 별도 프로세스로 실행된다.
- **NFR-1.2** 에이전트의 크래시·행업이 로봇 주행 기능에 영향을 주지 않아야 한다 (watchdog에 의한 자체 재시작만 수행).
- **NFR-1.3** CPU 사용률 상한: 기본 1코어의 20% 이하 (Bulk 압축 작업 제외 시), 설정으로 조정 가능. cgroup/nice 적용 권장.
- **NFR-1.4** 메모리 상한: 기본 512 MB 이하 (디스크 버퍼 별도).
- **NFR-1.5** 구독으로 인해 퍼블리셔측 부하가 증가하지 않도록 best-effort QoS를 기본으로 한다.

### NFR-2. 네트워크 및 성능
- **NFR-2.1** 평시(상태+이벤트) 업링크 대역폭: 로봇 1대당 기본 상한 1 Mbps 이하, 설정 가능. 목표 평균 100~300 kbps.
- **NFR-2.2** 상태 데이터 종단 지연(로봇 발행 → 서버 수신): 평시 1초 이하.
- **NFR-2.3** 이벤트 데이터 종단 지연: 평시 500 ms 이하.
- **NFR-2.4** Bulk(온디맨드) 요청-응답: 스냅샷 1장 기준 3초 이내 (네트워크 정상 시).
- **NFR-2.5** 대역폭 상한 초과 시 우선순위 기반으로 자동 절제(throttle)되어야 하며 연결이 붕괴되어서는 안 된다.

### NFR-3. 신뢰성
- **NFR-3.1** 5분 이내의 네트워크 단절에서 이벤트 데이터 손실 0건.
- **NFR-3.2** 재연결 성공까지 평균 10초 이내 (네트워크 복구 시점 기준).
- **NFR-3.3** 에이전트 비정상 종료 시 10초 이내 자동 재시작, 재시작 후 디스크 버퍼 데이터 복구.
- **NFR-3.4** 72시간 연속 운영에서 메모리 누수·성능 저하 없음.

### NFR-4. 확장성
- **NFR-4.1** 서버측 관점에서 로봇 50대 동시 접속을 전제로 한 네임스페이스·인증 체계를 갖춘다 (브로커 자체 부하는 서버 프로젝트 범위).
- **NFR-4.2** 로봇 1대에서 파이프라인 30개 이상 동시 처리 가능.
- **NFR-4.3** 신규 샘플러/코덱/전송 구현 추가 시 기존 코드 수정 최소화 (플러그인 등록만으로 확장).

### NFR-5. 보안
- **NFR-5.1** 서버 통신은 TLS 1.2 이상 암호화.
- **NFR-5.2** 로봇별 개별 인증 정보(client credential 또는 인증서) 사용. 유출 시 개별 폐기 가능해야 한다.
- **NFR-5.3** 인증 정보를 코드/저장소에 하드코딩하지 않는다.
- **NFR-5.4** 다운링크 명령의 발신자 인증 및 권한 검증은 서버측 책임으로 하되(→ 서버 프로젝트), 에이전트는 NFR-7의 안전 검증(TTL·멱등성·레지스트리 등록 여부·스키마)을 독립적으로 수행한다. 서버가 뚫려도 에이전트가 마지막 방어선이다.

### NFR-6. 유지보수성·이식성
- **NFR-6.1** 대상 ROS2 배포판: (확정 필요 — 예: Humble) / Ubuntu 22.04+.
- **NFR-6.2** 단위 테스트 및 통합 테스트(가상 토픽 발행 → 리시버 수신 검증) 제공.
- **NFR-6.3** rosbag 재생 기반의 재현 가능한 성능 테스트 시나리오 제공.
- **NFR-6.4** 문서화: 설정 스키마 레퍼런스, 샘플러/코덱/전송 확장 가이드.

### NFR-7. 다운링크 안전 (Safety-Critical — 협상 불가 조항)

> ⚠️ **본 절은 협상 불가(non-negotiable) 안전 요구사항이다.** 다운링크는 실제 차량의 거동을 유발할 수 있는 채널이므로, 본 절의 요구사항은 일정·편의를 이유로 생략할 수 없으며, 추후 재검토 시에도 **완화가 아닌 구체화 방향으로만** 수정한다. 세부 수치(TTL 기본값, 등급 기준)는 잠정값이며 운영 경험에 따라 조정하되, 각 메커니즘의 존재 자체는 조정 대상이 아니다.

- **NFR-7.1 (TTL 필수)** TTL이 없는 명령은 수신 즉시 거부한다. `issued_at + ttl`이 경과한 명령은 절대 실행하지 않고 `expired`로 응답 후 폐기한다. 특히 네트워크 단절 중 브로커에 적체된 명령이 재연결 시 일괄 유입되는 상황에서, 만료 명령의 지연 실행("10분 전 목적지 명령이 갑자기 실행됨")은 어떤 경우에도 발생해서는 안 된다.
  - TTL 기본값(잠정): 주행·작동 명령(L2) **30초**, 설정성 명령(L1) **5분**, 조회성 명령(L0) **5분**. 인터페이스 등록 시 `default_ttl`로 지정하며, 명령 envelope의 ttl은 이를 초과할 수 없다.
- **NFR-7.2 (멱등성)** 동일 `cmd_id`의 명령은 재전송·중복 수신되어도 정확히 1회만 실행한다. 에이전트는 최근 처리한 cmd_id 캐시를 유지하며, 중복 수신 시 기존 결과를 재응답한다.
- **NFR-7.3 (안전 기능의 다운링크 비의존)** E-Stop, 충돌 회피, 지오펜스 등 안전 기능은 차량 자체 시스템에 존재해야 하며 다운링크에 의존해서는 안 된다. 다운링크는 운영 편의 채널이지 안전 채널이 아니다. 다운링크 전면 장애 상태에서도 차량은 안전하게 동작·정지할 수 있어야 한다.
- **NFR-7.4 (권한 등급)** 모든 인터페이스는 위험도 등급을 갖는다: **L0**(조회) < **L1**(설정 변경) < **L2**(작동·주행 유발). 등급은 레지스트리 등록 시 필수 지정 항목이다. v1에서 에이전트는 등급 필드의 존재와 envelope 정합성을 강제하며, 발신자 신원 인증과 등급별 권한 검증의 완전한 구현은 서버 프로젝트에서 수행한다 — 단, 그 전까지 L2 인터페이스의 운영 환경 사용은 금지한다 (테스트 환경 한정).
- **NFR-7.5 (검증 없는 실행 금지)** 에이전트는 레지스트리 등록 여부 → payload 스키마 → TTL → 멱등성의 검증 체인을 모두 통과한 명령만 실행하며, 이 순서와 각 단계는 코드상 우회 경로가 존재해서는 안 된다.
- **NFR-7.6 (감사 추적)** 모든 다운링크 명령의 수신·검증 결과·실행 결과는 로컬 감사 로그와 서버 보고 양쪽에 기록되어, 사후에 "언제 누가 어떤 명령을 보냈고 차량이 어떻게 처리했는지"를 재구성할 수 있어야 한다.
