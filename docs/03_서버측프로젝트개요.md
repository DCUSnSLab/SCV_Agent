# (향후 별도 프로젝트) Fleet Telemetry Server — 개요 메모

> 본 문서는 차량측 에이전트(FTA) 프로젝트의 후속으로 진행될 서버측 시스템의 방향성 메모이다. 지금 당장 진행하지 않으며, FTA 설계 시 인터페이스 정합성을 확보하는 용도로만 참조한다.

## 1. 역할
LTE/5G를 통해 올라오는 최대 50대 로봇의 텔레메트리를 수신하여 (1) 저장, (2) ROS2 bag 기록, (3) 웹 모니터링 시스템 등 클라이언트로의 실시간 중계를 수행하는 중앙 수집 플랫폼.

## 2. 구성 (초안)

```
로봇 × 50 ──▶ MQTT Broker (EMQX 등, HA 구성)
                  │
                  ▼
            Ingestion Service
            ├─ envelope 디코딩 / 검증 / robot_id 라우팅
            ├─ ① 시계열 저장:  상태·이벤트 → TimescaleDB/InfluxDB
            │                  Bulk(이미지 등) → 오브젝트 스토리지(MinIO)
            ├─ ② rosbag2 기록: payload가 CDR 원본이므로 재직렬화 없이
            │                  로봇별/세션별 bag 파일로 직접 기록 가능
            └─ ③ 실시간 중계:  WebSocket/SSE 게이트웨이 → 웹 모니터링 UI,
                               필요 시 서버측 ROS2 도메인으로 재발행(rviz 등 기존 툴 재사용)
```

## 2.1 다운링크 관련 서버측 책임 (FTA v1에 다운링크가 포함됨에 따라 추가)
- **인터페이스 레지스트리 DB + 웹 등록 UI**: 개발자가 다운링크 인터페이스(이름, kind, ros_type, target, 스키마, 권한등급 L0~L2, TTL)를 등록·관리. FTA의 테스트 레지스트리 도구가 정의한 retained 메시지 포맷이 계약.
- **명령 발행 API**: 웹 클라이언트 요청 → 명령 envelope(cmd_id, issued_at, ttl, issuer, payload) 생성 → `fleet/{robot_id}/cmd/{interface}` 발행, `cmd_result` 수신·전달.
- **발신자 인증·권한 검증**: NFR-7.4의 등급별 권한 체계 완전 구현은 서버 몫. 이것이 완성되기 전까지 L2(주행 유발) 인터페이스는 테스트 환경에서만 사용한다는 제약을 승계함.
- **registry_status 활용**: 로봇별 지원 인터페이스 보고를 수신하여 UI에서 "이 로봇에 이 명령 가능 여부"를 표시.

## 3. FTA와의 인터페이스 계약 (이 부분이 지금 중요)
- MQTT 토픽 네임스페이스: `fleet/{robot_id}/{class}/{pipeline}`, 다운링크 `cmd`/`cmd_result`, 레지스트리 retained 채널 (02 문서 §3.7, §3.11)
- Envelope 스키마: 02 문서 §3.4 — **이 스키마가 두 프로젝트 간 계약이며, 버전 필드를 두어 호환성을 관리한다.**
- payload 기본 CDR 원본 유지 → 서버측 rosbag 기록·ROS2 재발행 비용 최소화 (이 설계 결정의 수혜자가 서버 프로젝트).

## 4. 주요 검토 과제 (서버 프로젝트 착수 시)
- 브로커 선정·이중화, 로봇 인증 체계(인증서 발급/폐기 운영)
- 저장 계층: 시계열 DB 선정, 보존 주기, Bulk 스토리지 정책
- rosbag 기록 단위(세션/시간/미션별) 및 재생 도구 연계
- 실시간 중계 프로토콜(WebSocket vs ROS2 재발행 vs 둘 다)과 구독 권한
- Kubernetes 배포 (기존 랩 인프라·연구와 연계 가능)
- 50대 규모 부하 테스트 (FTA의 테스트 리시버 → 부하 생성기로 발전시켜 재활용 가능)
